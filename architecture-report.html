1. Use Determinate as an executable. Do not copy its code.

Determinate Systems has already built and tested the hard native Base Nix work. This includes daemon setup, services, build accounts, platform files, repairs, and uninstall behavior. pkg should use that work through the released installer executable.

Determinate owns Base Nix

  • Create and maintain machine-wide /nix.
  • Install the Nix daemon and native services.
  • Create the required build users and groups.
  • Own its vendor receipt and native integration files.
  • Perform supported Base Nix repair and terminal uninstall.

pkg owns the product

  • Let the person install pkg first.
  • Authenticate and start the pinned Determinate executable when Base Nix is absent.
  • Manage package selection, generations, roots, garbage collection, and package repair.
  • Own pkg journals, receipts, services, commands, and user messages.
  • Clean pkg-owned package state before an explicit terminal Base Nix uninstall.

2. Step-by-step install and lifecycle design

The person installs pkg only. pkg handles the Base Nix dependency as part of its own first-run flow.

  1. Inspect the machine.pkg checks the Determinate receipt, real Nix behavior, known services, and conflicting Nix evidence. It does not trust one marker alone.
  2. Classify the Base Nix state.A supported Determinate installation continues. A clean machine can install. Foreign or mixed Nix state stops with a clear message. pkg does not take over unknown state.
  3. Select one approved installer.The release manifest names an exact Determinate version, platform asset, size, and SHA-256 digest. There is no moving “latest” input.
  4. Authenticate before execution.pkg verifies the downloaded or bundled bytes. A digest or identity mismatch stops before privilege is requested.
  5. Use a clean process contract.pkg passes only approved arguments and a fixed environment. It does not inherit unsafe proxy, shell, or path values by accident.
  6. Write a small handoff record.The record says which approved installer pkg started. It helps crash recovery. It does not claim that Nix is healthy.
  7. Let Determinate perform native work.Determinate owns all Base Nix writes. pkg does not create /nix, launchd services, systemd services, or build accounts in parallel.
  8. Verify the result.After the process finishes or the machine reboots, pkg checks the vendor receipt and real machine behavior. It then marks the handoff complete.
  9. Continue with pkg package work.pkg now installs the requested packages. Package generations and product repair remain pkg duties.
  10. Keep uninstall explicit.Removing one package cannot remove Base Nix. A separate terminal command first cleans pkg-owned package state, then calls the supported Determinate uninstall, then checks residue.

There is one Base Nix writer. pkg authenticates, delegates, verifies, and then continues with product work.

Defect one: the operation lock parent

The old macOS operation lock was /private/var/run/pkg-install-handoff.lock. On real macOS, /private/var/run is owned by root:daemon and has mode 0775. Group members can write there.

The shared parent-chain security check correctly rejects any group-writable or world-writable ancestor. DeterminateHandoff::state() takes the operation lock before it reads the handoff. The clean-host preflight therefore failed at the lock. Determinate never started. The lock moved to /private/var/db and the strict parent rule stayed.

The security rule stayed strict. Only the macOS lock location changed.

Defect two: the ancestor group rule

Workflow-12 run 33258481980 passed every hosted gate and then stopped before Handoff at /Library/Application Support. The shared ancestor checker required GID 0. Real macOS keeps that directory as root:admin with mode 0755. Fix 337ba704 accepts exact safe root-owned ancestors, keeps UID root, keeps the directory type, keeps no-follow traversal, and still rejects every group or other write bit.

Defect three: the vendor temp directory

Workflow-13 run 33264502945 passed every hosted gate. The slot 1 install then reached the vendor installer for the first time. The Determinate installer exited 1 inside setup_default_profile. The product hides vendor output by design, so a private diagnostic on the failed host reproduced the failure and captured the vendor error.

The product ran the vendor with TMPDIR=/private/var/db/pkg-install/tmp. The product created and required that directory, and every parent, to be exactly mode 0700 and root-owned. The vendor's setup_default_profile step runs nix build as the unprivileged _nixbld users. Those users must stat TMPDIR while they set up a build environment. A 0700 root-only directory chain denies that stat, so the build fails with Permission denied and the vendor installer exits 1.

The control experiment proved the direction: the same production invocation with a root-owned, traversable temp directory completed the vendor install with exit 0. Linux never hit this because the Linux build sandbox does not stat the inherited TMPDIR as a build user.

No unprivileged write is allowed in either path. The new path only adds traversal for the vendor's build users.

9. Security boundaries that must stay

Authenticate before privilege

Verify exact bytes, digest, release identity, and manifest before the installer can make machine-wide changes.

One native writer

Determinate writes Base Nix state. pkg never writes the same state in parallel.

Fail closed on unknown state

Foreign Nix, mixed receipts, unsafe ancestors, wrong ownership, wrong mode, or stale proof identity stop the operation.

Do not hide local-admin limits

A local administrator can change the executable or machine after verification. pkg protects the release and execution boundary. It cannot defeat the machine owner.

  • Do not weaken parent directory validation to make macOS pass.
  • Do not trust a pkg handoff marker as proof that Base Nix is healthy.
  • Do not use a local certificate authority or local proof server as release proof.
  • Do not expose short-lived runner credentials in logs, files, or reports.
  • Do not publish any private alpha proof inputs.
  • Do not allow a package removal command to call terminal Base Nix uninstall.
  • Do not keep temporary GitHub environment tag policies after proof.

3. The shipping trust flow

The proof branch fixed a real trust error. A package digest is not trusted because it appears beside a release tag. The signed SHA256SUMS file must bind the package, CLI, release manifest, and their digests.

The proof reuses the product trust system. It does not add a local certificate authority, a private HTTP server, or a second channel format.

Why two signed package tags cannot prove N-to-N+1 by themselves

Both packages contain the same live channel URLs. If the live channel already points to N+1, the package called “N” also reads N+1. The tags prove which package bytes were shipped. They do not freeze the channel state that the package reads.

An honest upgrade proof needs two immutable staged channel states. The runner must install N while the channel is pinned to N. Then an authorized publisher must advance the same real channel route to N+1. Only then can the runner prove a native N-to-N+1 product upgrade.

Accepted direction

2. Why the recommendation changed

The first architecture had a different ownership rule. pkg tried to own a private Nix runtime. The Broker and Root Helper protected that private runtime. Raw Nix was treated as hidden system detail. That rule made direct upstream reuse difficult.

  1. Earlier rulepkg owned the private runtime, privileged writes, repair, and uninstall behavior. An upstream installer that owns machine-wide /nix did not fit that rule.
  2. New product choiceThe user accepted machine-wide /nix. The user also accepted Determinate ownership of base Nix install, repair, update, and uninstall.
  3. New UX ruleRaw Nix stays outside the normal product PATH and UX. It is still discoverable by absolute path. It is not secret. PATH is not a security boundary.
  4. New threat limitA local administrator can change the machine. This is outside the supported threat model. A checksum cannot secure a machine that an administrator already controls.
  5. Smallest correct boundaryWith those choices accepted, a pinned vendor executable becomes the smallest complete machine-wide boundary. pkg can call it as a subprocess and keep product package work separate.

8. Security, failure, and crash rules

Security improvements

  • One exact vendor asset replaces a broad custom machine-wide implementation.
  • SHA-256 verification happens before execution.
  • A fixed absolute path prevents PATH binary substitution by normal callers.
  • A clean environment removes caller-selected Nix URLs, planners, and flags.
  • One vendor receipt gives base Nix one machine authority.
  • Foreign Nix is refused instead of silently adopted.

Accepted limits

  • A local administrator can replace files, change services, edit PATH, or run raw Nix.
  • Raw Nix outside normal PATH is a UX rule only.
  • A checksum does not protect a compromised release manifest, build system, signing process, vendor release, or administrator-controlled machine.

Remaining supply-chain risks

pkg still trusts the selected vendor revision, release asset production, the pkg release manifest, pkg distribution, and the digest review process. If the asset is downloaded, pkg also depends on source availability. The checksum protects integrity against a different byte stream. It does not prove that approved bytes are safe.

Fail-closed behavior

  • Digest mismatch: do not execute.
  • Unsupported platform: do not execute.
  • Foreign Nix: do not install over it.
  • Missing or damaged receipt with existing Nix: enter Unknown and stop.
  • Unexpected vendor exit: keep diagnostic evidence and do not mark Ready.
  • Post-install behavior mismatch: do not enable package work.

Crash and power-loss behavior

Before execution, pkg writes only a small handoff marker with the pinned contract identity. During execution, Determinate owns its machine transaction. After a crash or reboot, pkg reads the vendor receipt and real machine behavior. It never turns its marker into machine authority.

Crash R1 is an accepted negative observation. The vendor recovery install exited 0, but the later state check failed because _nixbld1 was missing. Functional Nix recovery was not reached. The DN-06 checkpoint in the grouped DN-05–07 PR must not use SIGKILL or accept exit 0 alone. Its DN-07 checkpoint must validate Handoff and state. The DN-12 checkpoint in the grouped DN-08–14 PR may run an optional repair sequoia proof. DN-16 remains blocked until the full crash and reboot lifecycle passes twice.

6. Exact operator steps for upgrade or repair

  1. Stop the product units while their files are trusted.sudo systemctl stop pkg-nix-broker.service pkg-root-helper.service pkg-nix-broker.socket pkg-root-helper.socket
  2. Disable the product units while their files are trusted.sudo systemctl disable pkg-nix-broker.service pkg-root-helper.service pkg-nix-broker.socket pkg-root-helper.socket
  3. Remove product unit drop-ins.Do this before the installer runs. The fixed fragments must resolve under /usr/lib/systemd/system.
  4. Run one operation.Use no option for upgrade. Use --repair-product-assets for same-release Product Asset Repair.
  5. Activate after success.Run sudo systemctl daemon-reload. Then use systemctl enable --now for the four units. Or enable the units and reboot.
Do not change service state during the installer run.

pkg rechecks service state before product-file writes. Another root process can still change state between a query and a write. The checks reduce this time-of-check/time-of-use window. They cannot remove it against a concurrent root administrator.

Do not stop a service through an untrusted unit file.

systemctl stop can execute a changed ExecStop. systemctl disable can interpret changed install rules. Take the service set offline while product files are still authenticated. If damage happened first, use a trusted rescue procedure. The alpha repair command refuses active or enabled services. It does not make them safe.

Retry safelyUse the same mode and matching installer schema.

  • A pending Offline Upgrade must continue as Offline Upgrade.
  • A pending Offline Repair must continue with --repair-product-assets.
  • A mode mismatch is refused. pkg does not reinterpret durable state.
