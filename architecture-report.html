Product

What pkg does

pkg is a terminal tool for Linux and macOS. Nix is its package engine.

One install

The person installs pkg

The person does not install Nix first.

Automatic base

pkg installs Determinate Nix

When the Nix base is absent, pkg automatically verifies and runs a pinned Determinate Nix Installer binary. Determinate then owns machine-wide Nix install, repair, and uninstall.

Product work

pkg manages packages

People can search, install, update, remove, roll back, and repair packages. pkg owns package choices, per-user state, generations, and package operations.

Accepted direction

2. Why the recommendation changed

The first architecture had a different ownership rule. pkg tried to own a private Nix runtime. The Broker and Root Helper protected that private runtime. Raw Nix was treated as hidden system detail. That rule made direct upstream reuse difficult.

  1. Earlier rulepkg owned the private runtime, privileged writes, repair, and uninstall behavior. An upstream installer that owns machine-wide /nix did not fit that rule.
  2. New product choiceThe user accepted machine-wide /nix. The user also accepted Determinate ownership of base Nix install, repair, update, and uninstall.
  3. New UX ruleRaw Nix stays outside the normal product PATH and UX. It is still discoverable by absolute path. It is not secret. PATH is not a security boundary.
  4. New threat limitA local administrator can change the machine. This is outside the supported threat model. A checksum cannot secure a machine that an administrator already controls.
  5. Smallest correct boundaryWith those choices accepted, a pinned vendor executable becomes the smallest complete machine-wide boundary. pkg can call it as a subprocess and keep product package work separate.
Small example

A person installs pkg on a clean Mac. pkg sees that the Nix base is absent. pkg obtains one exact installer asset, verifies its SHA-256 value, and runs it with a clean fixed contract. Determinate creates and owns the base Nix system. pkg then installs the packages that the person selected.

5. One vendor receipt and one pkg handoff marker

The vendor receipt is the authoritative record for the base Nix installation. pkg reads it. pkg never edits it. The pkg handoff marker records only that pkg completed or started its own handoff. The marker is not machine authority.

AbsentNo supported base receipt or install evidence exists.
Provisioningpkg started a verified vendor operation and wrote a small handoff marker.
ReadyThe vendor receipt and required base behavior agree.
UnknownEvidence is missing, damaged, or contradictory. Stop and diagnose.
Unsupported existing NixA foreign Nix installation exists. Refuse automatic takeover.

If the receipt is damaged or missing while /nix still exists, pkg enters Unknown. It must not rewrite the receipt, silently declare success, or take ownership of the existing installation.

Accepted direction

6. Step-by-step product and base workflows

Normal package work and base Nix work are separate commands and separate ownership paths.

  1. Fresh installThe person installs pkg. pkg sees no supported Nix base. pkg obtains the exact installer asset, verifies it, runs it from a fixed absolute path with a clean environment, waits for completion, validates the vendor receipt and required behavior, records its small handoff marker, and then allows package work.
  2. Existing Determinate Nixpkg reads the vendor receipt and checks supported base behavior. If the state is Ready, pkg does not reinstall Nix. It continues to pkg-owned package work.
  3. Existing foreign Nixpkg detects Nix evidence without the supported Determinate authority. It enters Unsupported existing Nix. It explains the conflict and refuses automatic takeover or deletion.
  4. Package install or updateThe Application seam handles the typed package request. pkg resolves catalog and policy, updates per-user Manifest and Lock, performs package execution through its Nix adapter, creates a generation, activates it, and reports progress. Normal package update never updates base Nix.
  5. Package removepkg removes the selected product package from user state and creates the next generation. Package remove never uninstalls Nix.
  6. User-state repairpkg repairs Manifest, Lock, generations, activation, and pkg-owned roots. It does not edit the vendor receipt or repair machine-wide Nix.
  7. Base-Nix repairAn explicit base repair command checks the supported state and delegates to the verified Determinate executable. pkg reports progress and result. Determinate owns all machine-wide writes.
  8. Explicit base-Nix uninstallA separate explicit command warns that the package engine will be removed. It checks pkg-owned package state, applies product cleanup policy, and delegates the base uninstall to Determinate. It then verifies that owned residue is gone. A package removal command cannot reach this path.
  9. Base-Nix updateA separate explicit command selects a newly approved pinned Determinate contract. It is not part of normal package update. It must test upgrade and downgrade refusal rules before release.
Command separation example

“Update my editor” changes a pkg package generation. “Update the Nix base” invokes an explicit Determinate-owned lifecycle. These two actions do not share an update switch.

PATH is a blocking compatibility gate

Raw Nix must stay outside the normal pkg PATH and UX. This is a product compatibility rule. It is not secrecy and it is not a security boundary. A local administrator can use an absolute path and can change system configuration.

  • Prove behavior in a login shell.
  • Prove behavior in a non-login shell.
  • Prove the GUI and macOS launch environment.
  • Prove that repair does not expose raw Nix in normal PATH.
  • Prove that base update keeps the PATH rule.
  • Prove that uninstall removes any owned PATH integration.
Stop condition

If the pinned installer cannot meet the PATH contract across these environments, stop the migration. Do not claim that one installer flag solves the problem.

Accepted direction

8. Security, failure, and crash rules

Security improvements

  • One exact vendor asset replaces a broad custom machine-wide implementation.
  • SHA-256 verification happens before execution.
  • A fixed absolute path prevents PATH binary substitution by normal callers.
  • A clean environment removes caller-selected Nix URLs, planners, and flags.
  • One vendor receipt gives base Nix one machine authority.
  • Foreign Nix is refused instead of silently adopted.

Accepted limits

  • A local administrator can replace files, change services, edit PATH, or run raw Nix.
  • Raw Nix outside normal PATH is a UX rule only.
  • A checksum does not protect a compromised release manifest, build system, signing process, vendor release, or administrator-controlled machine.

Remaining supply-chain risks

pkg still trusts the selected vendor revision, release asset production, the pkg release manifest, pkg distribution, and the digest review process. If the asset is downloaded, pkg also depends on source availability. The checksum protects integrity against a different byte stream. It does not prove that approved bytes are safe.

Fail-closed behavior

  • Digest mismatch: do not execute.
  • Unsupported platform: do not execute.
  • Foreign Nix: do not install over it.
  • Missing or damaged receipt with existing Nix: enter Unknown and stop.
  • Unexpected vendor exit: keep diagnostic evidence and do not mark Ready.
  • Post-install behavior mismatch: do not enable package work.

Crash and power-loss behavior

Before execution, pkg writes only a small handoff marker with the pinned contract identity. During execution, Determinate owns its machine transaction. After a crash or reboot, pkg reads the vendor receipt and real machine behavior. It never turns its marker into machine authority.

Crash R1 is an accepted negative observation. The vendor recovery install exited 0, but the later state check failed because _nixbld1 was missing. Functional Nix recovery was not reached. The DN-06 checkpoint in the grouped DN-05–07 PR must not use SIGKILL or accept exit 0 alone. Its DN-07 checkpoint must validate Handoff and state. The DN-12 checkpoint in the grouped DN-08–14 PR may run an optional repair sequoia proof. DN-16 remains blocked until the full crash and reboot lifecycle passes twice.

12. Rollback and stop conditions

The migration must have one writer at each machine-wide step.

  • Never run the old custom installer and Determinate as equal writers.
  • Do not silently take over foreign Nix.
  • Do not delete old code until the matching proof gates pass.
  • If PATH behavior fails, stop the migration.
  • If install, repair, update, uninstall, receipt, or crash recovery cannot meet the contract, stop the migration.
  • If the executable contract has one proven blocking gap, write the gap down and make a new explicit fork decision. Do not drift into copied source.
Rollback during delivery

Before the new path becomes authoritative, keep the current path unchanged except for required safety fixes. If a spike fails, remove the thin experimental adapter and keep the current alpha. Do not leave both models enabled.

  2. Per-user authoritative state. User package state stays user-owned. In the current alpha, shared authenticated data stays broker-owned.
  3. Broker and Root Helper privilege split. This earlier alpha decision is superseded for machine-wide Nix work. Determinate now owns that lifecycle. The current path remains until replacement gates pass.

Approved DN-15 architecture

The Linux installer now has three simple modes

This section is the current design. Earlier sections remain below as the history that led to it. The code and local tests exist. The final native x86-64 proof does not exist yet.

1. The result in plain language

Fresh host

Install and start

pkg verifies and runs Determinate once when Base Nix is absent. It installs product files. It then enables and starts the fixed product services.

Existing product

Upgrade while offline

The operator stops and disables product services. pkg replaces authenticated product files. pkg does not change service state.

Damaged product file

Repair while offline

The operator uses the same release. pkg replaces the damaged product file with authenticated same-release bytes. Services stay offline.

This is not a Base Nix repair.

Determinate alone owns Base Nix. Product Asset Repair can change product files only. Package Repair remains a different command for damaged Nix store content.

3. Fresh Install: install Base Nix once, then activate pkg

  1. Authenticatepkg authenticates the product release and the pinned Determinate Nix Installer 3.22.1 executable.
  2. Install Base Nixpkg records Started. It starts Determinate once. One supervisor drains bounded output, waits, and reaps.
  3. Accept the handoffOnly vendor exit status 0 plus installed-state validation becomes Accepted.
  4. Activate productpkg installs exact product files. It enables and starts the four fixed product units. The product receipt is published last.
Command and success message

sudo ./pkg-install

pkg is installed.

Fresh retry after Base Nix is Accepted

A crash can happen after Base Nix is Accepted and before product installation finishes. pkg keeps the Fresh Install recovery. The operator runs the same authenticated installer again without an option. pkg does not start Determinate again.

Exact retry message

Base Nix is ready, but pkg product installation is incomplete. Run pkg-install again.

4. Offline Upgrade: the operator owns the service window

  1. Stop and disableThe operator makes all four product units inactive and disabled.
  2. Query onlypkg checks unit state, exact fragment paths, and the absence of drop-ins. It does not run a systemd mutation command.
  3. Replace product filespkg authenticates N+1. It replaces only product-owned files. Base Nix Handoff and user package state stay in place.
  4. Activate laterpkg leaves services offline. The operator inspects the result, reloads systemd, and activates the new release or reboots.
Command and success message

sudo ./pkg-install

pkg product files are upgraded. Product services remain offline.

This design deletes active-upgrade service recovery. There is no service state to restore because pkg never changes service state during the upgrade.

5. Offline Repair: move forward to known same-release bytes

  1. Use the same releaseThe operator uses the authenticated installer that matches the installed product receipt.
  2. Prove offline stateAll four units must be inactive and disabled. Their fragments must be exact. Drop-ins must be absent.
  3. Repair files onlypkg replaces receipt-owned product files with authenticated same-release bytes. It never keeps or restores unknown damaged bytes.
  4. Stay offlineEvery retry checks offline state again. Success, failure, and recovery leave services inactive and disabled.
Command and success message

sudo ./pkg-install --repair-product-assets

pkg product files are repaired. Product services remain offline.

Repair refuses a directory, account, unrecorded file, wrong-release receipt, missing receipt, damaged ownership record, active unit, enabled unit, changed fragment, drop-in, or failed systemd query. It fails before product-file mutation when the preflight is unsafe.

6. Exact operator steps for upgrade or repair

  1. Stop the product units while their files are trusted.sudo systemctl stop pkg-nix-broker.service pkg-root-helper.service pkg-nix-broker.socket pkg-root-helper.socket
  2. Disable the product units while their files are trusted.sudo systemctl disable pkg-nix-broker.service pkg-root-helper.service pkg-nix-broker.socket pkg-root-helper.socket
  3. Remove product unit drop-ins.Do this before the installer runs. The fixed fragments must resolve under /usr/lib/systemd/system.
  4. Run one operation.Use no option for upgrade. Use --repair-product-assets for same-release Product Asset Repair.
  5. Activate after success.Run sudo systemctl daemon-reload. Then use systemctl enable --now for the four units. Or enable the units and reboot.
Do not change service state during the installer run.

pkg rechecks service state before product-file writes. Another root process can still change state between a query and a write. The checks reduce this time-of-check/time-of-use window. They cannot remove it against a concurrent root administrator.

Do not stop a service through an untrusted unit file.

systemctl stop can execute a changed ExecStop. systemctl disable can interpret changed install rules. Take the service set offline while product files are still authenticated. If damage happened first, use a trusted rescue procedure. The alpha repair command refuses active or enabled services. It does not make them safe.

7. Crash, retry, and refusal rules

AuthenticateBind one exact product release.
JournalRecord mode and intent before a file change.
MutateRecheck offline state for existing-install work.
Receipt lastPublish ownership only after exact files exist.
Retry safelyUse the same mode and matching installer schema.
  • A pending Fresh Install must continue as Fresh Install.
  • A pending Offline Upgrade must continue as Offline Upgrade.
  • A pending Offline Repair must continue with --repair-product-assets.
  • A mode mismatch is refused. pkg does not reinterpret durable state.
  • An unsupported recovery schema is left unchanged. The matching installer must finish it.
  • An older, newer, or malformed product receipt is not migrated by upgrade or repair. pkg refuses it and keeps it for review.
  • Upgrade rollback uses authenticated prior receipt bytes.
  • Repair recovery rolls forward to authenticated same-release bytes.

10. Deliberate alpha limits

  • Foreign Nix, upstream Nix, unmarked Determinate Nix, and unclear ownership fail closed.
  • A persisted Base Nix Started state remains an Unknown Base Nix Outcome. pkg does not retry it.
  • Determinate can leave vendor-owned residue after uninstall. pkg records it. pkg does not build a cleanup engine for it.
  • Product Asset Repair is Linux-only and same-release only.
  • Offline upgrade and repair need an operator service window.
  • Concurrent root mutation can still race a state query. Operators must not change product units during the operation.
  • Old Linux Base Nix code stays until DN-17. Deletion follows native replacement proof.
  • macOS stays separate until Apple Silicon lifecycle, APFS, launchd, crash, and reboot proof pass.
