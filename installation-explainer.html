0. The whole story in plain words

What installing pkg means

pkg is a package manager that runs on top of Nix. When you install it, two things land on the machine: a Base Nix (the Nix daemon and store, installed and owned by the Determinate installer), and the product (the pkg CLI, a broker, a root helper, and their services — owned by pkg itself).

Everything the installer needs comes from one place: a signed channel — an HTTPS directory of artifacts whose fingerprints are listed in signed TUF metadata. The installer carries the trust anchor (a root key) baked inside itself, fetches the channel, verifies every byte, installs Base Nix through the pinned Determinate installer, then installs the product on top.

The rule for users

A user never types a flag, a URL, or an environment variable. Those exist for the maintainer, the CI, and constrained hosts only. If an alpha install ever requires a user to set an env var, the design has failed.

2. What the installer does, phase by phase

2.1 The three Linux install modes

ModeWhenServicesWhat changes
Fresh Install clean host, no previous pkg activated by the installer Base Nix + all product assets; the only mode that starts services
Offline Upgrade (N → N+1) existing install, new release must already be inactive + disabled product files only; systemd is queried, never commanded; operator activates after
Offline Repair damaged same-release files must already be inactive + disabled rolls damaged files forward to the authenticated same-release bytes

Offline modes exist so an upgrade or repair can never run a changed binary inside a live service. macOS adds a store-preserving uninstall path and a terminal vendor uninstall; see section 3.4.

3. Determinate Nix inside pkg

3.1 Who owns what

In plain words

pkg never builds a second Nix installer and never repairs the vendor's half of the world. If the vendor has no supported operation for something, pkg reports it as unsupported. One lifecycle engine per layer — that is the whole design.

3.2 The Base Nix handoff — the safety core

Why so strict, in plain words

Once the vendor installer is running, the pinned version gives pkg no safe way to cancel, signal, time out, or watch it die. Vendor output is diagnostic, not a protocol. So pkg writes Started to disk first, starts the vendor exactly once, and waits. If the machine or the vendor dies mid-way, nobody can prove what state Base Nix is in — so pkg refuses to guess. Exit 0 alone is not proof either; only exit 0 plus finding the installed executable and a valid receipt becomes Accepted.

3.3 How the vendor is invoked

/nix/nix-installer (from the channel, digest-pinned, exec bit forced, absolute path)
  --diagnostic-endpoint <pinned> install --determinate --no-confirm --no-modify-profile
  [--extra-conf <value>]        ← only when PKG_DETERMINATE_EXTRA_CONF is set (PR #16)

environment: scrubbed to HOME, PATH, TMPDIR (private, 0700), telemetry disabled
supervision: one supervisor drains bounded stdout+stderr, waits, reaps
             no second start, no signals, no hard timeout — ever
uninstall:    exec /nix/nix-installer uninstall --no-confirm /nix/receipt.json
              (product cleanup finished and handoff consumed first; plain output only)

Constrained hosts (emulated x86_64 containers) cannot load the seccomp syscall filter that Determinate Nix enables by default. The remedy is one environment variable, and the installer prints the hint when the vendor fails that way: PKG_DETERMINATE_EXTRA_CONF='filter-syscalls = false'. Note the spaces — the vendor rejects sandbox=false without them.

3.4 What uninstall does

  1. Refuses structured output modes on a live uninstall (plain terminal only).
  2. Finishes and verifies every product-owned cleanup action first.
  3. Under the stable lock: revalidates the exact /nix/nix-installer and the opaque /nix/receipt.json.
  4. Consumes the Accepted handoff, then execs the vendor uninstaller as the very last action.
  5. Vendor-owned residue is reported and left alone — accepted alpha limit.

4.4 The Nix daemon configuration

The daemon's nix.conf is rendered from authenticated channel inputs (the managed build configuration), not edited by hand. pkg is the one writer. Local administrators may still change machine-wide Nix directly — that is allowed, not a security boundary — but pkg doctor detects important changes and fails closed where ownership is unclear. Raw Nix can coexist on the machine; pkg keeps it out of the normal user experience.

5. When it fails — and what you will see

The new failure contract (landing now)

Every failure prints three things: the phase, a stable code, and — for vendor failures — the vendor's own stdout/stderr, bounded. Tonight's debugging turned every mystery into a one-line answer once these existed. The temporary DIAG prints used to find them get stripped; the reporting stays.
