### BUG-01: one connection cancels another connection's work

Reproduction with the main CLI:

1. Start `pkg remove ripgrep` in terminal A. Leave the confirmation open.
2. Run `pkg doctor --json` in terminal B as the same user. It exits 0 and reports
   `healthy`.
3. Answer `y` in terminal A. Removal exits 79, `ENGINE_UNAVAILABLE`.

An alpha.54 install also failed after a concurrent doctor check. The same
install completed when run alone. In cases 35–36, a later `pkg pin fzf` returned
an unchanged pin result but recovered and applied the previously failed removal.

`pkg-installer/src/broker.rs:585` calls `caller.disconnect()` when a transport
connection ends. `pkg-nix/src/broker.rs:1596` selects every running operation
with the same UID. It has no connection owner check. The main-library probe
observed `(Cancelled, false)` for the other connection's operation and build
gate; the expected result was `(Running, true)`.

Bind automatic disconnect cleanup to the connection's operations. Preserve the
explicit authenticated reconnect/reconciliation path. Test two connections
with the same UID during preparation, approval, build, root publication, and
repair. Keep different-UID and owner-disconnect controls.

### BUG-02: mixed operation recovery can become stuck

This uses ordinary commands after the interrupted removal from BUG-01. No
state file was edited for this reproduction.

1. With active `gen-0011`, start removal of fzf, run doctor in another terminal,
   and approve removal. It fails and leaves prepared `gen-0012`.
2. Run `pkg install hello --on-collision keep-first --yes --json`. It succeeds
   and activates `gen-0013`, whose parent is `gen-0011`.
3. Run `pkg pin fzf`, `pkg remove hello --yes`, or `pkg rollback --yes`.
   Each exits 73, `STATE_CORRUPT`.
4. Run `pkg repair --yes`. It reports `clean`. Retrying pin still exits 73.

The journal has only a `prepared` row for generation 12. Generation 13 has
prepared, rooted, activated, and committed rows. Both records name generation
11 as parent. The final doctor still reports healthy.

`commands/local.rs:773` runs only install recovery before a new install.
`recover_pending_install_with` filters to install/upgrade records. State edits
instead enter `recover_pending_state_edit` at line 1287.
`pkg-pipeline/src/commit.rs:510` refuses to resume a prepared state edit when
its parent is no longer current. The new install made that condition permanent
for the tested mutation commands. Repair does not reconcile this journal state.

Reconcile all pending transaction kinds before any new mutation. A prepared
generation must not be skipped by a different command family. Add a matrix of
interrupted operation → next operation tests, including install after remove
and remove after install. Verify the active state, journal, roots, and usable
commands after recovery. Do not classify pending records as completed history.

### BUG-03: broken commands receive a clean repair result

Remove only the user-owned `current/bin/rg` activation link. Leave the store
output intact. `doctor --json` reports `healthy`. Both `repair --verify-only`
and `repair --yes` report `status: clean` and exit 0. `rg --version` still fails
with command not found. Repeating the test with fzf and the main CLI has the
same result. The links were restored after each test.

`DoctorReport::evaluate` in `commands/doctor.rs:319` checks state-root permissions,
not generation, journal, or activation integrity. `repair_with_broker` loads
the immutable snapshot, but `load_active_snapshot` does not verify the forest.
The production repair authority at `production_repair.rs:59` derives store
closure roots from the helper and verifies that closure. It never repairs the
user activation tree. The CLI nevertheless calls the generation clean.

Verify the recorded activation digest and entries in the user-state layer.
Report damage during verification and rebuild the forest from verified state
when repair is requested. Keep store verification and activation verification
explicit in machine output. Add missing-link and wrong-link target cases.

### BUG-04: an empty environment is not a helper failure

Removing all three installed selectors succeeded and created empty generation
10. `pkg list --json` returned an empty array. Both repair modes then exited 77
with `the privileged repair helper refused the operation`. Rollback succeeded.

Empty generations deliberately have no helper root set:
`pkg-pipeline/src/commit.rs:847` returns no root transition intent.
`pkg-installer/src/production_repair.rs:59` still requires a root-set attestation
for every generation. The resulting missing set becomes a permission error.

Handle verified empty generations explicitly without requesting a nonexistent
root set. Test remove-last → verify → repair → rollback.

### BUG-05: failure after the current switch loses the outcome

The fault fixture temporarily replaced the mutable `lock.json` view with a
directory. Immutable snapshots and store paths were untouched.
`pkg unpin fzf --json` then exited 73 and said that the state change could not
be committed. However, current advanced from generation 7 to 8 and fzf was
already unpinned. Doctor reported healthy. Restoring the view path and running
pin recovered the transaction and created generation 9.

`ActivatedGeneration::finish` returns `ActivatedNeedsRecovery` when mutable
view restoration fails. `commands/local.rs:1269` maps that distinction to a
generic error and sets `local_committed` only after `finish` succeeds. The
operation has already crossed the current-switch boundary.

Retain the post-activation outcome in the CLI and machine result. State that
the change was applied and recovery remains necessary. Do not advise a blind
retry as if nothing changed. Exercise failure at each write after activation.
This test did not show store data loss or removal of durable roots.

### BUG-06: dry-run does not validate the install against active state

`pkg install fzf --dry-run --json` returned `ok: true` although fzf was already
installed. The real request exited 65, `PREFLIGHT_FAIL`, after acquisition work.
With a saved keep-first collision between catalog just and flake just, an
unrelated hello preview also succeeded; the real request exited 71 under the
default abort policy. No activation warning appeared in either preview.

`commands/local.rs:770` returns from the dry-run branch before reading the
active snapshot. `preview_install` at line 2073 only asks for a build preview.
It receives neither the active state nor the collision policy.

Validate known duplicate selectors and available activation conflicts before
reporting a ready install plan. Distinguish checks that cannot finish until
outputs are available. Preserve read-only behavior. The default abort policy
itself is not counted as a separate defect here.

### BUG-07: install's keep-going option is unused

`pkg install no-such-one no-such-two --keep-going --yes --json` reports one
generic resolution error. Neither failed selector is identified. The option
promises to resolve every target. `InstallArgs::keep_going` is defined in
`cli.rs:527`, but the production install path never reads it. The only runtime
`args.keep_going()` use is in unsupported-upgrade option rejection.
`pkg-pipeline/src/resolve.rs:134` collects a `Result<Vec<_>, _>` and stops at
the first resolution error.

Implement bounded per-selector resolution results without partial commit, or
refuse the option explicitly until it is supported. Test multiple failures.

### BUG-08: orphan-check records a request without doing the work

`pkg remove fzf --orphan-check --dry-run --json` returns only the ordinary
removal fields plus `orphanCheckRequested: true`. A real ripgrep removal has
the same omission. There are no closure candidates, byte estimates, or an
explicit unavailable result.

The help at `cli.rs:543` promises collectible-closure preview.
`commands/state.rs:165` only copies the boolean into the result. No collector
or preview consumes it. Implement the promised retained-generation-aware
check, or reject the unsupported flag. Test both preview and actual removal.

### BUG-09: repeated shell setup grows MANPATH

With one documented shell setup line, evaluating `pkg shellenv` twice more
changed one pkg man-directory entry to three identical entries. PATH remained
deduplicated. `pkg-cli/src/path.rs:155` and line 167 prepend MANPATH without
the guard used for PATH. Nested shells also inherit and extend this value.

Make both shell snippets idempotent while preserving the empty MANPATH entry
that requests system defaults. Cover Bash and zsh.
