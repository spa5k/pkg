# BUG-02: recover pending work before a new mutation

The fix gives install, upgrade, remove, pin, unpin, update, rollback, GC,
history deletion, and mutating repair one recovery path. Recovery runs before
these commands select their source state or decide that no change is needed.
Generation preparation checks again under its exclusive lease. Prune and
repair also check after taking their mutation lease.

The original [bug audit](BUG-HUNT-2026-09-26.md) records the failure. This fix
is local and unreleased. The release remains deferred.

## Recovery rules

- Complete pending prunes and discard work that never reached preparation.
- Resume prepared state edits. Reconcile installs against durable helper roots.
- Preserve forward recovery when the pending generation is already active.
- An old CLI can leave an unactivated attempt beside a newer committed sibling
  with the same parent. Discard only that verified superseded attempt, using
  the existing journaled, root-last cleanup. Keep the newer current generation.
- Refuse other divergent histories. Do not guess which state the user intended.
- Discover aborted state edits after a crash before prune intent, as for installs.
- Show only committed generations in completed history. An active but unfinished
  generation requires recovery. Verify-only repair reports pending recovery
  without changing state and directs the user to mutating repair.

## Native VM proof

In `pkg-bug02-final-20260926`, the published CLI still failed `pin fzf` with
73/`STATE_CORRUPT` in case 13. In case 14, the final CLI succeeded on the same
state. Generation 13 stayed current. Its four packages remained installed;
hello and fzf executed. Verify-only repair passed. Pending generation 12 was
aborted and pruned, rather than applied over generation 13.

Cases 15–17 repeated an interrupted removal followed by a new install. The
published CLI left fzf removal pending after another terminal ran doctor.
The fixed CLI completed that removal before installing ripgrep. The new
install's parent is the recovered removal generation. Pin, another removal,
rollback, ripgrep, and hello then succeeded.

In the development VM, case 10 used the final CLI to verify a different pending
removal. Verify-only repair exited 72/`STATE_LOCKED` without applying it. Case 11
ran `repair --yes`, completed the removal, verified the resulting generation,
and installed hello successfully. The journal is retained in case 12.

Both test VMs are stopped. This is native macOS regression evidence. It is not
Linux runtime evidence, production trust approval, or a release installation.
