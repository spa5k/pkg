## macOS test isolation finding

The first final-source macOS hermetic CI attempt failed an immediate state-lock
reacquisition after a lease was dropped. A documentation-branch run exposed the
same class of failure in the verify-only repair test. Concurrent shell-spawning
unit tests can fork while another thread holds a file lock. The child retains
that open file description until exec; close-on-exec does not prevent this
short interval. The source review found no missing Rust lease drop.

A native fork probe and concurrent process-spawn probe reproduced the mechanism.
The retained spawn run observed 35 transient conflicts across 82,878 lock cycles
and 821 child spawns, with a maximum wait of 255.042 microseconds. Thirty local
CLI suite repetitions (191 tests each) passed. The final-source CI passed one
justified rerun of the failed job with the source unchanged. The failed attempts
and probe remain in the evidence. VERIFY-01 retains test isolation work; do not
weaken active-lease refusal or add production retries to hide this test race.

The same final release had already completed just in the native upgrade proof.
The fresh public VM also passed acquisition. After review, one unchanged hosted
rerun was permitted as a controlled repeat. It failed at the same point. Further
runs add diagnostic evidence rather than repeat the same observation. The corrected hosted-capacity run completed on Linux and macOS.
It used the unchanged signed alpha.56 product files..
The original attempts remain in the evidence. A successful repeat cannot explain
that earlier failure. [PR #66](https://github.com/spa5k/pkg/pull/66) now retains bounded broker-stage
logs in public macOS CI. A later [diagnostic run](https://github.com/spa5k/pkg/actions/runs/36241872641)

(exit 65). The earlier recorded load was 10.88 on three logical CPUs; the product
ceiling is six. The failure happened 71 seconds later and groups disk/load
checks, so this does not prove which resource failed at that moment. A sandboxed
