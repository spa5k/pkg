pkg · planning change · 28 September 2026 · plan only, not implemented

Generate the Cask catalog with Rust.
Build it with plain Nix.

A maintainer tool converts one pinned Homebrew Cask snapshot into a deterministic catalog. A standard flake builds packages from that data with generic builders. The client reads status from one generated index and keeps the native profile lifecycle. No token lists, no hardcoded app names, no Brew, no Ruby, no hosted service.

OpenSpec change · design · tasks · full plan

Summary

Today three hand-picked tokens on aarch64-darwin flow through the pinned brew-nix converter with a Nix classifier, curated lists, one hand-written override, and a client constant (CASK_SYSTEM). This plan replaces all of it:

  • tools/cask-catalog — a maintainer-only workspace member. fetch pins the snapshot (revision + SHA-256, the only network step); generate runs offline and deterministically, producing schema pkg-cask-catalog/2: per-target eligibility, bounded exclusion reasons, typed artifact plans, resolved cask dependencies, provenance. Atomic: any integrity failure leaves outputs untouched.
  • nix/casks — one flake, one input (pinned nixpkgs), generic data-driven builders ported from brew-nix (MIT attribution kept): app archive, binary, pkg payload, AppImage via Nixpkgs appimageTools.wrapType2. Lazy per token; import-from-derivation stays disabled; no per-package files; the brew-nix input is removed after the port.
  • pkg client — thinner: one index envelope (catalogIndex) with an explicit target list; search filters locally with a declared Rust-regex grammar; info/install use the ordinary flake attribute and expand the cask closure; the classifier, CASK_SYSTEM, and pkg-cask-support/1 are deleted.

Required packaging fix: the release license collector currently reads whole-workspace metadata. It must walk only pkg-cli's resolve graph for the packaged target, and the archive must be checked to contain no generator binary, maintainer-tool license, or catalog data. Owned by phase RC-01.

Dataflow

brew-api snapshot @ exact rev
   │  cask-catalog fetch        (only network step; verifies sha256)
   ▼
nix/casks/catalog/input.json    (single pin: url, rev, sha256, license)
   │  cask-catalog generate     (offline, deterministic, atomic)
   ▼
nix/casks/catalog/catalog.json  ── committed together, reviewed ──┐
   entries[token].targets[sys] = eligible (typed plan)            │
                                 | excluded (bounded reason)      ▼
                                                      nix/casks flake (nixpkgs only)
                                                        ├ packages.<sys>.<token>  (lazy builds)
                                                        ├ catalogIndex            (one envelope)
                                                        └ catalogStatus           (coverage)
                                                                   │
CI: regenerate from pin, fail on diff                             ▼
                                                        pkg client: read targets first;
                                                        search = envelope + local regex;
                                                        info/install = ordinary attr,
                                                        gate on generated status,
                                                        install expands cask closure;
                                                        native profile lifecycle unchanged

Key rules: OS support comes only from explicit constraint fields (supported_platforms, depends_on) — never from variation keys or artifact kinds; a snapshot losing a required field fails closed; formula dependencies exclude the token (no guessed nixpkgs names, no committed map); vendor strings are always data; unknown tokens never become eligible; verified is observational evidence, never an install gate.

Acceptance

  • CI regeneration from the committed pin is byte-identical; provenance names input revision, hash, generator version; duplicate tokens, conflicting versions, pin mismatch, and missing required fields abort with no output replaced.
  • Index and per-token builds evaluate with IFD disabled; one token builds without forcing others; pre-write path checks, the pkg relocatable-layout rule, bounded autoPatchelf closure, and AppImage wrapping hold; no system or vendor installer ever runs; no essential pkg payload is silently dropped.
  • Status and search rows share one locked revision; broad search forces no derivations; missing targets are detected from the envelope; excluded and unknown tokens are refused with reasons; schema mismatch names both schemas; installs expand the cask closure; native upgrade still follows the moving reference; no Homebrew cleanup hooks run.
  • Evidence recorded: Linux binary + AppImage runs (E2B, headless — runnable claims only); macOS app+CLI launch with codesign --verify --deep --strict (Tart VM); coverage counts labeled as eligibility, not compatibility; archive free of generator artifacts and maintainer-tool licenses.
  • CI green across the two-member workspace; docs-linkcheck green.

Not acceptance criteria: universal Cask support, formula resolution, fonts, services/drivers, macOS Intel or Linux arm64, GUI launch claims from headless runs, any fixed eligible count.

Risks and outstanding constraints

  • Strict field requirement: a mirror bump dropping supported_platforms fails generation until the source or rule is revisored — intended fail-closed behavior.
  • Formula exclusions are broad: every formula-dependent cask is excluded in this change; reviewed resolution may come later. No guessed names.
  • Eligible ≠ works: builds may fail lazily on first request; coverage counts expose the gap. Pending probes (1password-cli binary, koreader AppImage) are running in a second sandbox — not claims yet.
  • pkg pass rate may be low: the relocatable-layout rule is strict; widening is a future reviewed change, not per-token overrides.
  • Packaging: without the RC-01 collector fix, maintainer-tool licenses would ship with the client; the fix is a prerequisite and is re-verified at release.
  • Verification split: Linux evidence is headless; macOS evidence depends on the parent's Tart VM. Claims stay within what each environment can prove.
  • Two-system scope: other systems need new verification, not a list edit.

Standing constraints: no token allowlists; no hardcoded app names; no manual package maps; no hosted API or database; no Brew/Ruby runtime; no vendor installer execution; no Homebrew cleanup hooks; no per-package Nix files; no compiled Rust shipped to users; import-from-derivation disabled; original moving references preserved; declared macOS baseline 15.7 compared by major and minor.
