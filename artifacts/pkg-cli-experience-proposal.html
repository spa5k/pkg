01 / The problem

Say what changed. Say when it changed.

Today, pkg install cask:stats can print installed stats before macOS app setup ends. If the app helper then fails, the command ends with a long chain of Nix build errors. The user sees success first and failure last.

Proposed rule: A completed success line is the last line of a successful transaction. If package state changed but app setup failed, report partial completion. Name the part that worked, the part that failed, and the next command.

CURRENT 01

Noise hides the action.

Native build output can show store paths, derivation names, repeated dependency errors, and a long diagnostic tail.

CURRENT 02

Some status is hard to use.

pkg list prints short names. pkg remove requires exact profile entry IDs. The two views must agree.

CURRENT 03

Read operations can be verbose.

pkg update prints source revisions and cache counts. pkg doctor prints details for healthy parts.

CURRENT 04

Failures can repeat themselves.

Search source failures and nested Nix errors can appear more than once. One clear error should lead the output.

Evidence in current main: crates/pkg-cli/src/commands/lifecycle.rs, commands/query.rs, commands/doctor.rs, commands/tap.rs, commands/mod.rs, nix/report.rs, and output.rs. Example names and counts below are illustrative.

02 / Output rules

One status model for all commands.

RuleProposalReason
Default detailShow the action, a useful working stage, and one final result.Short output is easier to scan.
Working outputOn a terminal, update one status line. In a pipe, print only stage changes.Progress stays readable in logs.
DiagnosticsShow the first useful cause once. Put full Nix output under --verbose. Show nix log <drv> when a derivation is known.The cause stays visible without an error cascade.
Truthful resultsRead actual profile state before the final line. Report Unchanged when nothing changed. Report package state and app state separately if needed.A command must not claim work that did not finish.
Output streamsSend progress and diagnostics to stderr. Send final query data and successful result lines to stdout. Send failed final results to stderr.Scripts can read data without progress text.
Machine outputKeep the current --json scope and schema. Print no decoration in JSON, shellenv, or completion output.These outputs are consumed by other tools.
ConsentKeep tap approval before any fetch or Ruby work. Do not hide the repository or approval scope.The prompt supports a real choice.
ColorUse color as a hint only. Keep words, signs, and exit codes useful with --no-color.Output must work in plain text.

Compact result pattern: Installed: stats, Unchanged: stats is already installed, or Partial: stats is installed; app launcher setup failed. Put a next step on the next line only when the user can act on it.

ExitMeaningOutput rule
0Complete or unchangedState what is true now.
1Failed or partialState the confirmed change, the cause, and one useful next step.
2Invalid command useShow the bad argument and valid syntax.
130Interrupted native operationRead the profile again. Say what changed or say that the state is unknown.
03 / Stage model

Show only stages that happen.

01 / CHECK

Check the request.

Resolve the target. Stop early on an unknown name or invalid input. Show choices when a name is ambiguous.

02 / PLAN

Show a plan when it matters.

List exact targets before broad upgrades, removals, and generation deletion. Keep tap approval explicit.

03 / WORK

Show useful progress.

Use short verbs such as Fetching, Building, Updating profile, and Setting up apps. Do not show Nix store paths by default.

04 / RESULT

State the final state.

Use Installed, Removed, Updated, Unchanged, Partial, or Failed. Do not call the same action both installed and failed.

A query command can go straight from check to data. Do not print an empty progress stage for a fast command.

Interrupted work: Print Interrupted: install stopped. Then print the verified profile state. If the profile cannot be read, print Package state is unknown. Do not guess from the last progress line.

04 / Command examples

Each command, in context.

The examples show proposed text. A blank stage means the command has no work to report. Entry IDs and counts are examples.

A

Find and inspect

pkg search QUERY query

Show installable IDs first. Show a source warning once.

PlanNone

05 / Build order

Fix the harmful cases first.

OrderChangeAcceptance check
1Move final success after app setup in install, remove, upgrade, and rollback. Add a verified partial result.The Stats helper failure never prints a complete Installed line.
2Reduce nested Nix errors to one cause and one detail route. Keep all raw output under --verbose.A failed build shows one cause and one nix log path when known.
3Make list show exact entry IDs. Make upgrade results match actual changes.A copied ID works in remove; an unchanged entry is not called upgraded.
4Shorten search, update, doctor, and tap output. Keep query JSON unchanged.Healthy and no-op cases fit in one or two useful lines.
5Use one shared formatter for statuses, hints, tables, and exit classes.TTY, pipe, --no-color, JSON, and shell output follow the same rules.
06 / References

Patterns from other package tools.

These are design references. The example output above is a proposal for pkg. It is not a copy of another tool.

  • pacman The official pacman manual documents transaction operations, query modes, confirmation controls, and quiet output. Borrow its clear boundary between package selection and a state change.
  • Homebrew The official Homebrew manual separates search, info, install, update, and upgrade. Borrow its short action labels and clear command scope.
  • paru The official paru manual describes interactive selection and a review path for source build files. Borrow its clear choice point. Keep pkg tap approval before the first fetch.
  • winget The official winget documentation separates search, show, list, install, upgrade, and uninstall. Its troubleshooting guide explains verbose logs. Borrow the split between default output and diagnostic detail.
Scope: current origin/main command set at review time. This file is a design proposal. It does not change CLI behavior or the published JSON schema.
