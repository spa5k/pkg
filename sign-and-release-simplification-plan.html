Plan artifact · proposal for discussion

One chain, one key, one command

A simpler sign and release model for pkg. The current model proved the product. It is too heavy for personal testing, for alpha releases, and for the production trust ceremony. This plan cuts the moving parts and keeps the security that matters — and it releases from your laptop or from GitHub CI, so no release ever depends on one device.

0. The plan in plain words

This page is technical. This section is not. If you read only one section, read this one.

What the product needs, in plain words

When pkg installs or updates, it downloads files and must be sure they are the files you published. The method is like a sealed catalog with a signature: every file has a fingerprint (a SHA-256 digest), the fingerprints are written in a signed list (TUF metadata), and the machine checks the signature and the fingerprints before it installs anything.

This is a good method. We keep it. The problem is everything around the method: the way the list is signed, the way the files are shipped, and the way a test run is prepared.

The five annoyances, in plain words
  1. The delivery address is printed on the can. Every binary has the channel URL baked in at build time. Move the channel and you must rebuild, re-sign, and re-publish everything. This is why a dead test URL forced new releases, and why the proof needs a private loopback server with its own certificate authority.
  2. The signing keys are born new every time. Each proof pair mints a fresh root key, signs once, and throws the key away. One small expiry (a 24-hour stamp) then forces a whole new key set. Keys should live for years, like a passport — not like a bus ticket.
  3. Two locks on one door. The files are authenticated twice: once by TUF, once by cosign/sigstore. Two stacks means two identities, two tag rules, and double the failure modes — for the same security result.
  4. The test needs a private cinema. To test the product you must recreate a fake channel inside a VM, with a self-made certificate, instead of pointing at a real shelf over HTTPS. That is the loopback server, the CA, and the keychain trust steps.
  5. Numbers are copied by hand. A proof dispatch needs 154 pin values copied from the mint into the workflow. Every new pair repeats the copying.
The fix, in plain words

Sign with one key set per environment that lives for years. Print the address on a label, not on the can — the product keeps the trusted key inside but takes the channel address at run time, over HTTPS only. Then one command does the whole publish and prints a small "release card" with all the numbers, so nothing is copied by hand.

You can run that one command in two places. On your laptop for quick work, or in GitHub CI for alpha, beta, and production releases — and even per pull request. The key is one encrypted file that lives in your secret store and on your machine. Your laptop is a convenience, not a requirement. If it dies, or you switch devices, releases continue from GitHub the same day.

One rule stays everywhere: every publish waits for your explicit approval — PR, alpha, beta, and production alike. A release is a deliberate act, never an automatic one.

1. Summary

The verdict in six lines.

  1. One trust chain. TUF metadata authenticates every artifact. The cosign / sigstore / GitHub-draft signer stack is deleted. It is a second signature stack for the same bytes.
  2. Long-lived keys. One root and one online key per environment, created once, kept encrypted, rotated rarely. The ephemeral-root re-key cycle is deleted.
  3. Channel is runtime, not baked. The product embeds the trusted root only. The channel URL is a validated runtime input. One build serves dev, proof, alpha, beta, and production channels.
  4. One command, two homes. pkg-rel publish builds, signs, uploads, and prints a release card. Run it on your laptop for quick work, or from GitHub CI for alpha, beta, production, and per-PR releases. The encrypted key lives in both places.
  5. Real HTTPS host. Channels live on static object storage under kelv.dev. The in-VM loopback server, per-run CA, and keychain trust disappear.
  6. Ceremony fits the threat model. One maintainer. Encrypted keys, recorded steps, and OS notarization. Not a 3-of-5 KMS ceremony. See section 6.
What does not change

The product TUF client, expiry enforcement, monotonic version checks, Base Nix Handoff, package lifecycle, and the two-slot lifecycle proof for milestones. This plan changes release tooling and key handling, not product trust behavior.

3. Root causes

D1 — The URL is baked at compile time

The product embeds root JSON, metadata URL, and targets URL in the binary. Every channel change requires a rebuild and the full sign chain. This single decision caused the dead tunnel URL, the loopback server, the per-run CA, and most re-mints.

D2 — Roots are ephemeral

--prepare creates a root, signs it, and discards the private key. Any expiry or mistake forces a complete re-key. TUF roots are designed to live for years.

D3 — Two trust stacks

Cosign/sigstore authenticates release assets. TUF authenticates the same bytes on the channel. Each stack has its own identity rules, tags, and failure modes.

D4 — Identity pinned to tags

The cosign signer identity and the proof harness are pinned to workflow tags. A workflow edit forces a new tag. Tags multiplied because the harness changed daily.

D5 — Proof formats, not product formats

Sealed pairs, inventories, bundle tarballs, and the 154-pin block exist only for the proof. They duplicate what a signed channel already proves.

D6 — Opaque errors

SignError::Filesystem is one variant for about twenty failure classes. Every map_err(|_| …) discards the real cause. The 24 h expiry cost a day to find.

4. Principles

  1. P1 — One chain. Every artifact has exactly one authenticating path in its environment.
  2. P2 — Long-lived identity. Keys outlive releases. Rotation is a rare, recorded procedure.
  3. P3 — Channel ≠ build. Builds carry the trust anchor. Channels carry content. The two change at different rates and must not be coupled.
  4. P4 — One command per operation. Any action a human repeats is one command with one printed result. No hand-copied pins, digests, or approval round-trips.
  5. P5 — No device is the source of truth. A release must be possible without any one laptop. The command runs locally or in CI; the key is one encrypted file available in both places. (new)
  6. P6 — Ceremony fits the threat model. Single maintainer = encrypted keys and recorded steps. KMS and threshold keys only when a second independent party exists.
  7. P7 — The proof uses the product pipeline. Harness-only machinery is limited to the harness. Proof inputs are ordinary channel content.

5. Target architecture

In plain words

Think of a shop shelf (the HTTPS channel), a signed price list (TUF metadata), and a stamp (the key). The product carries the stamp in its pocket and reads the shelf. Today the shelf address is printed on the product itself, the stamp is re-made for every delivery, and a second stamp exists for no extra safety. We keep one stamp per environment and let the shopper be told the shelf address at the door.

One shelf has several aisles: pull request, alpha, beta, production. The stamp decides which aisle a build may enter. Publishing is one action — done from your laptop or from GitHub.

5.2 Channels and stages

Two trust environments, several aisles per environment. A channel is a path on the host plus a root. Nothing else differs between stages — the same publish command, the same product build.

One rule for every lane: a publish happens only after the maintainer approves it. GitHub Environments provide the gate (required reviewer). Nothing publishes by itself — not a PR, not an alpha, not an automatic job. The cost is one approval click per publish. The local smoke lane needs no gate because it touches only the local machine.

Device change, in plain words

Your laptop is a convenience, not a requirement. The encrypted online key has four copies: your machine, the GitHub secret store, a USB stick, and Bitwarden. To release, you press "Run workflow" on GitHub and choose the lane — even with no laptop at all. To work locally again on a new machine, restore the key file from the USB stick or Bitwarden and the same command works. The root key never travels: it is only needed at key creation and rotation, which happen once a year at most.

The trade we accept, stated plainly

A copy of the test online key and the production online key lives in GitHub secrets. GitHub becomes a possible theft target for the online key. This is survivable: an online-key leak means re-key and re-publish under root v2 — no product rebuild, no user action. The root key, whose loss is the serious event, never enters CI. This is the standard single-maintainer trade, and it is what makes device-independent releases possible.

One constant module holds these values. The release card prints them. No environment variable can silently change production policy.

5.4 Runtime channel URL

The installer and the broker accept a channel URL from a root-owned source at run time: pkg-install --channel https://… or the service environment file. The existing HTTPS-only validator rejects everything else. The embedded root authenticates all content, so the URL choice is a delivery detail, not a trust decision.

Result: the alpha, dev, proof, and production binaries are the same build. The loopback server, per-run CA, keychain trust, and URL rebuilds disappear. A PR build and a production build differ only in the aisle (URL) they point at and the root they trust.

5.5 Release card

The publisher prints one JSON card per publish. It replaces the sealed pair, the inventories, the bundle tarball, and the 154-pin block.

{
  "schema": 1,
  "environment": "test",
  "lane": "alpha",
  "root_sha256": "…",
  "key_id": "…",
  "product_commit": "…",
  "channel_n":      { "url": "https://channel.kelv.dev/proof-n/",        "targets_sha256": "…" },
  "channel_n_plus": { "url": "https://channel.kelv.dev/proof-n-plus-1/", "targets_sha256": "…" },
  "installer": { "name": "pkg-aarch64-darwin", "sha256": "…", "length": … },
  "pkg_macos": { "name": "pkg-…-preview.pkg",  "sha256": "…", "length": … },
  "policy": { "timestamp_hours": 168, "snapshot_hours": 336, "targets_hours": 1440 }
}

The proof workflow takes five inputs: the card, its SHA-256, the environment, and the destructive confirmation. The card is the pin. Drift is impossible because the publisher emits it. For PR and alpha lanes the card is printed into the run summary and posted on the PR.

In plain words

Today the numbers travel by hand from the mint to the test script — 154 of them. In the target model the publish command prints one small card with the ten numbers that matter. The test script reads the card. If the card is wrong, the test refuses to start.

5.6 Why TUF only — the honest trade with sigstore

What each system gives you, in plain words

Both systems answer one question: did these files really come from the maintainer, and were they changed? They answer it differently.

TUF is a stamp you own. The signing key is yours. Your product checks the stamp, the freshness, and the file fingerprints itself, at every update, with no third party in the path. It protects the machine even when the download server is evil. The cost: you must protect the stamp — that is the key custody in section 6.

Sigstore (cosign, keyless) is a borrowed stamp with a receipt. GitHub CI asks a public notary for a short-lived certificate that says "this file came from the pkg repository's release workflow". The receipt is stored in a public log that anyone can audit. Benefits: there is no key for you to protect or leak, and outsiders can verify a release without trusting you or your channel.

The honest trade: the product never checks sigstore — it checks TUF. Sigstore serves human auditors, not the app. In this campaign it also caused the tag-pinned identity and the per-release approval dance, because the borrowed stamp must be tied to a specific workflow identity. Keeping it means two systems, two identities, and the audit log — for a benefit the product itself never reads.

Recommendation: TUF only, now. Add sigstore back later, without migration pain, only if one of these becomes true: outsiders must audit releases without trusting you, or a second maintainer joins, or a compliance requirement appears.

6. Production trust and release — the best way for this product

In plain words

For one person running one product, the right amount of ceremony is: keys that are hard to steal, steps that are written down, and the checks the operating system forces. A bank-vault ceremony with five keys and hardware tokens protects against a team of insiders. You do not have a team of insiders. Spend the effort on key custody, on a CI path that works without your laptop, and on Apple's notarization, which is not optional.

Adopt now
  • One offline root key per environment. Generate on a machine that never touches the network (a booted USB laptop is enough). Encrypt with age or GPG. Two encrypted copies on two media. The passphrase goes to a password manager, not to a file. It never enters CI.
  • One online key per environment, with four copies. ed25519, age-encrypted. One copy on the machine, one base64 copy in GitHub secrets with the passphrase in a second secret, one encrypted copy on a USB stick, and the passphrase in Bitwarden. A leaked online key means re-key and re-publish, which the runbook records. A lost laptop changes nothing.
  • Release from CI, not only from the laptop. A thin release.yml wrapper calls the same pkg-rel publish with the key injected from secrets. Stages map to GitHub Environments with protection rules: every lane waits for the maintainer's manual approval (required reviewer). A stable environment identity replaces the per-change workflow tags.
  • macOS Developer ID is mandatory, not optional. Gatekeeper will not accept an unsigned product for real users. productsign + notarytool + staple runs inside the publish command for beta and prod lanes. Enrollment is the long pole — start it now.
  • Static HTTPS hosting with immutable objects. No server process. Rollback = upload the prior snapshot files. Versioned object names make this safe. The CI accesses storage with OIDC-federated credentials tied to the environment, so no long-lived cloud key sits in secrets either.
  • Rotation escrow at root creation. Sign root v2 with root v1 on day one and store it offline. Losing the root key becomes a non-event.
  • A two-page runbook. Key custody, publish steps, the device-change procedure, rotation, compromise response, rollback. Written when the ceremony runs, not after.

Compromise response — one paragraph of the runbook

If the online key leaks: revoke it in a new root (root v2), re-publish the last good snapshot under the new key, bump every expiry, and force clients to refresh by publishing a new targets file. If the root key leaks: the product must re-bake the root at the next release; old clients expire out of the root window. If the channel host is defaced: clients reject bad signatures; republish the last good immutable snapshot and check the timestamp version monotonicity in the datastore. If a laptop dies: nothing to do — the CI lane keeps releasing, and the key file restores from the password manager onto the next machine.

◆ = phase gate. Each phase ships, tests, and deletes on its own. Nothing waits for a later phase.

P0 — Unblock the campaign (≈ 1 day)

  • Fix SignError to carry the underlying io error and the failing path.
  • Default PKG_TIMESTAMP_TTL_HOURS to 168 for proof mints.
  • Persist the campaign test root key (age-encrypted) so expiry stops forcing re-keys.
  • Gate: one fresh pair mints with the long TTL; the second-channel failure either reproduces with a named error or disappears.
  • Parallel: start Apple Developer enrollment now — it is the long pole.

P1 — Collapse the trust stack (≈ 4–6 days)

  • Product: channel URL becomes a runtime input; root stays baked; HTTPS validation unchanged.
  • Tooling: pkg-rel publish replaces prepare/publish/bind and the draft+cosign flow. It runs identically on the laptop and in CI — one code path, key injected from the environment.
  • Keys: pkg-rel key init per environment; long-lived; encrypted; one copy in CI secrets, one on the machine; never in git.
  • Delete publish-release.yml, sigstore assets, ephemeral re-key paths, committed signing-state/.
  • Gate: alpha release installs and updates through the TUF chain with no cosign step, from the laptop path.

P2 — Real hosting, CI lanes, fast loops (≈ 2–3 days)

  • Stand up channel.kelv.dev static objects for the test environment.
  • Add release.yml: dispatch lanes for PR (opt-in label), alpha, and proof pairs. Secrets hold the encrypted test key; every lane requires the maintainer's approval.
  • install.sh generator renders the stable URL from the release card.
  • pkg-rel smoke: personal install → update → repair → remove in minutes.
  • Trim prove.sh and the workflow: drop loopback, CA, tarball, and pin phases.
  • Gate: one alpha release and one per-PR build published from CI with no laptop involved; personal smoke test is three commands.

P3 — Production ceremony, scaled (≈ 3–5 days + enrollment)

  • One-time offline ceremony: root T and root P keys, rotation escrow, custody record. Root P never enters CI.
  • Developer ID cert in the secret store; notarization runs inside pkg-rel publish --lane beta|prod.
  • Beta and prod lanes enabled with environment gates; first production channel publish, signed package, kelv.dev/install.sh.
  • One milestone re-proof against the production channel; evidence archived.
  • Two-page ops runbook incl. device-change procedure; docs and README point at kelv.dev; proof-grade URLs retired.
  • Gate: clean-Mac install of the notarized package; repeat-run proof green; runbook review; a release done end-to-end from a fresh laptop with only the key file restored.

10. Open questions for the discussion

  1. Is TUF-only acceptable, or does the sigstore log have value you want to keep?
  2. Do you accept the runtime channel URL change in the product? It is the biggest single simplification and touches the installer and the broker service.
  3. Which lanes need a manual approval gate? Proposal: beta and prod yes; alpha and PR no.
  4. Confirm TUF-only (see 5.6 for the honest trade with sigstore).
  5. Confirm the big-exam cadence: full two-slot proof before every production release and before the first beta; smoke test after every release; no exam for PR/alpha.
