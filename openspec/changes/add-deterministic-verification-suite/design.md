# Design: Deterministic verification suite

## Context

The product is a Nix-based package manager that provisions via the Determinate installer, keeps
an install journal, publishes ownership receipts, and consumes a TUF-signed release channel. All
four correctness pillars (journal recovery, receipt exactness, channel verification, fault
recovery) were proven once each during DN-15/DN-16. This change makes those proofs repeatable
and mechanical instead of episodic.

## Goals / Non-goals

See proposal. Additional design non-goal: we do not pursue formal verification or model
checking; the budget is spent on repeatability and coverage instead.

## Decisions

### D1. Time injection, not clock freezing at the OS level

Ambient time is the largest hidden dependency. We inject a clock trait through the same
pathways the journal and receipt writers already use for test fakes. OS-level clock freezing
(libfaketime) is rejected: it breaks under macOS SIP and adds an environment dependency to the
very thing we are trying to remove.

### D2. Pinned inputs instead of live channel

The repeat-run proof consumes a sealed pair by SHA from the workflow artifact store — the same
mechanism the DN-16 proof used (`baae3f8b…`). No live server. The workflow builds its own
ephemeral in-job proof channel with the existing `serve_proof_channel.py`, which is already
TUF-correct; it simply runs inside the job, not on a developer laptop.

### D3. Golden bytes per platform, not per release

Golden files pin one representative release pair per platform (x86_64-linux, aarch64-darwin).
Re-generating goldens is a reviewed, deliberate act (`UPDATE_GOLDEN=1`), never a test escape
hatch. Goldens live in `crates/pkg-testkit/golden/` and are covered by the lint gate so they
cannot rot as production files.

### D4. Boundary inventory from code, not from documentation

The fault-injection matrix is generated by scanning the mutation call sites (the same write
primitives the journal wraps), producing an inventory file that lists boundary → covering test.
Completeness is checked in CI. This prevents the classic drift where documentation lists ten
boundaries and the code has fourteen.

### D5. Platform gates as predicates, not comments

`#[cfg(target_os)]` remains for compile-time splits, but verdict-level platform dependence uses
a runtime predicate plus the existing test-harness skip reporting, so `cargo test --workspace`
output shows `skipped (platform: …)` rather than a red X on a developer laptop.

## Risks / Trade-offs

- **Golden brittleness**: byte-pinning journals may flag intentional format changes. Accepted:
  format changes should be deliberate and reviewed; the golden diff makes them visible.
- **Proof runner cost**: the repeat-run proof uses the same runner pool as DN-16 (two Apple
  Silicon slots, one Linux staged host). It is manually dispatched, not scheduled, so cost
  stays event-driven.
- **Time injection scope creep**: threading a clock through every pathway touches many
  signatures. Mitigation: default implementation returns ambient time; only test construction
  overrides it, mirroring the existing `CommandExecutor` pattern in `real/process.rs`.

## Open Questions

- Should the determinism report gate merges to `main`, or run nightly first? Proposal: nightly
  first, gate after two clean weeks.
